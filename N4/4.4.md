# Конспект: отчёт 4.4 — CSRF

## Цель

Изучить CSRF (Cross-Site Request Forgery) на своём MVC-приложении, показать три вектора атаки (GET-удаление, POST-изменение, POST-создание) и реализовать защиту.

## Задание 1. Атаки на своё приложение

Атакующий сайт на `127.0.0.1:9999`, уязвимое приложение на `127.0.0.1:8080`. У жертвы cookie `token` (HttpOnly, SameSite не задан, Secure нет).

### Кейс 1.1. CSRF через GET: удаление статьи

- **Роут:** `/articles/(\d+)/delete`
- **Проблема:** `delete` удаляет статью без проверки метода, токена и владельца.
- **Эксплойт `evil.html`:** скрытые `<img src="http://127.0.0.1:8080/articles/7/delete">` и `<iframe>` на тот же URL.
- **Ход:** жертва открывает `evil.html` → браузер сам шлёт `GET /articles/7/delete` с cookie → статья удалена. Второй запрос (из iframe) вернул 404 «Статья не найдена», что подтверждает удаление.
- **Итог:** атака успешна.

### Кейс 1.2. CSRF через POST: изменение статьи

- **Роут:** `/articles/(\d+)/edit`
- **Проблема:** проверка `self.user is None` не помогает, т.к. пользователь восстанавливается из cookie, а она у жертвы есть. Токена и проверки владельца нет.
- **Поля формы:** `name`, `text`.
- **Эксплойт `evil-edit.html`:** скрытая форма на `/articles/6/edit` с `onload="document.f.submit()"` (name = «ВЗЛОМАНО ЧЕРЕЗ CSRF»).
- **Ход:** жертва открывает страницу → форма сама отправляется POST с cookie жертвы.
- **Итог:** статья изменена без ведома жертвы.

### Кейс 1.3. CSRF через POST: создание статьи

- **Роут:** `/articles/add`
- **Проблема:** `add` игнорирует `request.POST`, автор захардкожен (`set_author_id(1)`), токена нет.
- **Эксплойт `evil-add.html`:** автосабмитящаяся форма на `/articles/add`.
- **Ход:** жертва авторизована → открывает `evil-add.html` → форма отправляется → браузер прикладывает cookie (SameSite не задан) → статья создаётся.
- **DevTools → Network:**

| Параметр | Значение |
|----------|----------|
| Request URL | `http://127.0.0.1:8080/articles/add` |
| Method | POST |
| Status | 302 Found |
| Referer | `http://127.0.0.1:9999/evil-add.html` |
| Content-Type | `application/x-www-form-urlencoded` |

- **Итог:** статья создана от имени жертвы, атака успешна.

## Задание 3. Защита от CSRF

Все три вектора успешно эксплуатировались → защиты не было.

### 3.1. POST-запросы: Synchronizer Token Pattern

1. В конструкторе базового `Controller` генерируется токен `secrets.token_hex(16)`, сохраняется в cookie `csrftoken` (HttpOnly, SameSite=Lax) и передаётся в шаблон через `set_var('csrf_token', ...)`. Метод `set_csrf_cookie()` ставит cookie, если её ещё нет. Cookie аутентификации `token` в `sign_in` тоже получила `SameSite=Lax`.
2. Во все формы добавлено скрытое поле `csrf_token` (`edit.html`, форма удаления в `articles.html`). В `index` и `view` токен передаётся в шаблоны.
3. В `ArticlesController` добавлен `_check_csrf(request)`: сравнивает `request.POST['csrf_token']` и `request.cookies['csrftoken']`, при несовпадении или отсутствии выбрасывает `UnauthorizedException`. Вызывается в начале POST-веток `edit` и `add`.
4. В `edit` добавлена **проверка владельца** (`article.get_author_id() != self.user.get_id()` → исключение). В `add` автор берётся из сессии (`self.user.get_id()`, раньше был хардкод `1`), поля читаются из `request.POST`.

### 3.2. GET-запросы

- `delete` теперь **только POST**: если `request.method != 'POST'` → `UnauthorizedException('Метод не разрешён')`. Далее порядок проверок: `_check_csrf` → авторизация → владелец.
- В `articles.html` ссылка «Удалить» заменена на POST-форму с `csrf_token`.
- Побочный дефект: шаблон падал с `UndefinedError`, если у статьи нет автора (статьи с `author_id=1` из кейса 1.3). Исправлено проверкой `{% if article.get_author() %}...{% else %}---{% endif %}`.

### Проверка эффективности

| Атака | Результат после защиты |
|-------|------------------------|
| GET-удаление (`evil-delete.html`) | «Метод не разрешён», статья не удалена |
| POST-изменение (`evil-edit.html`) | «CSRF token invalid», статья не изменена |
| POST-создание (`evil-add.html`) | «CSRF token invalid», статья не создана |
| Легитимная форма с токеном | работает штатно, редирект 302 |

## Выводы

- **Причины уязвимости:** нет CSRF-токена и его проверки, GET меняет состояние, нет `SameSite` у cookie, нет проверки владельца.
- **Меры:** Synchronizer Token Pattern, `SameSite=Lax`, `delete` только POST, проверка владельца, исправлены хардкод автора и падение шаблона.
- После внедрения все три атаки перестали работать, корректные запросы работают.
- Реализация соответствует OWASP CSRF Prevention Cheat Sheet.
