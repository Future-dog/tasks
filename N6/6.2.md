# Конспект: практическая 6.2 — IDOR


**Цель:** исследовать код веб-приложения на IDOR (Insecure Direct Object Reference), найти точки несанкционированного доступа к объектам, предложить меры защиты.

## Теория

- **IDOR** — приложение принимает от пользователя идентификатор объекта, но не проверяет, имеет ли он право на этот объект. Пример: `/articles/15` → заменить на `/articles/16`.
- Затрагивает просмотр, изменение, удаление, загрузку файлов.
- **Аутентификация** — кто ты. **Авторизация** — что тебе разрешено с конкретным объектом. Факт входа ≠ доступ ко всем записям.
- Проверка прав — на сервере, при каждом запросе.

## Структура проекта

| Файл | Назначение |
|------|-----------|
| `routes.py` | URL → обработчики |
| `controller/article_controller.py` | просмотр, правка, добавление, удаление статей |
| `controller/controller.py` | общая логика контроллеров |
| `models/article.py` | модель статьи, проверка владельца |
| `models/active_record_entity.py` | получение и сохранение записей |
| `models/user.py` | модель пользователя |
| `models/user_auth_service.py` | аутентификация |
| `views/errors/401.html`, `403.html`, `404.html` | страницы ошибок |

Маршруты: `/articles`, `/articles/add`, `/articles/{id}`, `/articles/{id}/edit`, `/articles/{id}/delete`, `/articles/search`.

## Анализ конечных точек

- **Просмотр `/articles/{id}`** — владелец не проверяется. Это **не IDOR**, если статьи публичные; если должны быть приватными — нужна проверка.
- **Редактирование `/articles/{id}/edit`** — статья загружается по id → 404 если нет → 401 если не авторизован → 403 если чужая → правка только после проверки → CSRF для POST. Есть `Article.is_owned_by(user_id)`. IDOR не выявлен.
- **Удаление `/articles/{id}/delete`** — проверяются существование, авторизация, владелец, метод, CSRF. GET → **405**, нужен POST. IDOR не выявлен.
- **Добавление `/articles/add`** — автор берётся из сессии (`self.user.get_id()`), а не из формы. Это правильно. Полная проверка при запуске не проводилась.
- **Список и поиск** — сами по себе не IDOR; нужно смотреть, какие данные возвращаются и публичны ли статьи. Фильтрация — на сервере, не в шаблоне.

## Сводная таблица

| Точка | Риск | Результат |
|-------|------|-----------|
| GET `/articles/{id}` | просмотр чужой закрытой статьи | зависит от публичности статей |
| GET `/articles/{id}/edit` | доступ к редактированию | проверка владельца есть |
| POST `/articles/{id}/edit` | изменение чужой статьи | владелец и CSRF проверяются |
| GET `/articles/{id}/delete` | удаление через GET | запрещено (405) |
| POST `/articles/{id}/delete` | удаление чужой статьи | авторизация, владелец, CSRF есть |
| `/articles/add` | подмена автора | автор из сессии |
| `/articles` | раскрытие закрытых статей | нужна проверка требований |
| `/articles/search` | раскрытие через поиск | нужна проверка возвращаемых данных |

**Итог:** подтверждённых IDOR-маршрутов нет. Это вывод **статического анализа**; для подтверждения нужна проверка вживую с несколькими аккаунтами.

## Защита

1. **Проверка владельца** перед изменением/удалением:
   ```python
   if self.user is None:
       return unauthorized_response()
   if not article.is_owned_by(self.user.get_id()):
       return forbidden_response()
   ```
2. **Автор назначается на сервере** из сессии.
3. **Не менять данные через GET**; удаление — POST + проверка прав и CSRF.
4. **CSRF-токен** при изменении/удалении. Он не заменяет проверку владельца.
5. **Список и поиск** — ограничивать выборку в серверной логике/запросе к БД, а не прятать записи в HTML.
6. **Побочная находка:** в `active_record_entity.py` SQL по id собирается через f-строку → риск SQL-инъекции (не IDOR). Использовать параметризованные запросы.

## Рекомендации

1. Сохранять серверную проверку владельца при edit/delete.
2. Проверять права при каждом запросе, включая альтернативные маршруты и HTTP-методы.
3. Автор новой статьи — из сессии.
4. Не использовать GET для изменяющих операций.
5. Проверять CSRF.
6. Проверить список и поиск на утечки данных.
7. Автотесты с двумя пользователями (чтение, изменение, удаление чужих объектов).
8. Параметризованные SQL-запросы.
9. UUID и непредсказуемые id — только дополнительная мера, не замена авторизации.

## Заключение

Проверки авторизации и владельца есть в edit/delete, автор при добавлении берётся из сессии, удаление через GET запрещено, CSRF проверяется. Подтверждённых IDOR нет; публичный просмотр и поиск оценивать по требованиям конфиденциальности. Для окончательного вывода — практическая проверка с двумя пользователями.
